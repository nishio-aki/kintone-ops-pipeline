🚀 社内総合受付・リクエスト管理パイプライン
（kintone × GAS × Googleスプレッドシート × Looker Studio）

📌 概要
社内で発生する多様なリクエスト（総務・IT・設備など）を一元管理し、業務のボトルネック（リードタイム）を可視化・分析するためのモダンな内製ETLパイプラインです。

単に「動くシステムを作る」だけでなく、「現場の泥臭い運用（対面依頼など）の吸収」「入力ミスを防ぐガード」「ビジネスアワーを考慮した正確なリードタイム算出」、そして「アジャイルなスコープの割り切り」といった、実際の現場（Ops）で必ず直面する課題をシステムと運用の両面から解決するように設計しています。

🛠️ 技術スタック

ETL / バックエンド: Google Apps Script (GAS) ※ LockService による排他制御実装

データストア (SSOT): Google スプレッドシート

BI / 可視化: Looker Studio

💡 設計のこだわり・工夫したポイント（アピール所）
1. 入力防御とプロセス管理（UX & ガバナンス）
ステータス逆流の防止: kintoneの「プロセス管理」を厳格に設定し、ユーザーが不自然なステータス遷移（例：完了から未アサインへの逆戻り）を起こせないよう物理的にロック。

クライアントサイド・バリデーション: JSを用いて、必須項目の抜けや不整合をリアルタイムで検知・ブロック。

2. 「現場の泥臭さ」をシステムに包摂するチャネル分離設計
課題: 「システムを通さず口頭・対面で頼まれた依頼」が現場では必ず発生する。これを完全に無視すると、システム外のシャドウワークが増えてデータが信頼できなくなる。

解決策: 大カテゴリ（IT・総務など）とは別に、「受付チャネル（通常 vs オフライン事後登録）」という軸を独立して設計。

「オフライン（事後登録）」を選択すると、過去の日時（受付・着手・完了）をまとめて入力できる専用フィールドが動的に出現。

BI側でのデータ分離: Looker Studioで正確な自動計測リードタイムを出す際は、フィルターでオフラインデータを安全に除外・分離できる構造にし、「分析の信頼性」と「運用の柔軟性」を両立させました。

3. 堅牢なETLとマルチスレッド対策（GAS）
IDベースのスマートなステータス更新: リクエストIDをキーにしてスプレッドシートを照合し、新規追加 (appendRow) と既存行の更新 (switch 文によるタイムスタンプのピンポイント上書き) を自動判別。

LockService による排他制御: 同時多発的なリクエストによるデータの競合・破損を防ぐため、GAS側にタイムアウト付きのロック機構（デッドロック回避設計）を実装し、システムの安定性を担保。

4. 営業時間・土日を考慮した「リアルな実稼働時間」の算出ロジック
課題: 単なる「着手から完了までのカレンダー上の経過時間（単純な引き算）」でリードタイムを測ると、夜間や土日をまたいだタスクが一律で「遅延扱い」になってしまい、正確な業務のボトルネックが見えなくなる。

解決策: GAS（またはスプレッドシート）において、以下のビジネスアワー補正アルゴリズムを実装。

土日除外: 期間に含まれる土曜日・日曜日を自動判定して稼働日数から除外。

営業時間外のカット: 1日のうち規定業務時間外（夜間・早朝）の経過時間を差し引き、「真に人間が動いていた実稼働時間（ビジネスアワー）」を算出。

成果: Looker Studioで表示される平均リードタイムやファネル分析の信頼性が劇的に向上し、どこのプロセスで本当に業務が滞っているかを正確に可視化。

🎯 今後の拡張性（Future Improvements）
MVP（実用最小限の製品）としてスピードとシンプルさを最優先し、一部の過剰な複雑さはあえてスコープ外として割り切っていますが、実運用や大規模展開を見据えた以下の拡張設計を想定しています。

真の冪等性（Idempotency）の担保:

現在はリトライ時の微小なタイムスタンプ上書きを許容する設計としているが、決済や厳密な監査ログなど「二重処理が絶対に許されないドメイン」へ拡張する場合を見据え、すでにタイムスタンプが刻まれたセルへの二重上書きをガードする条件分岐を追加する余地を持たせています。

通知・アラート機能の高度化:

スプレッドシート側で「一定時間（例: 3日以上）ステータスが動いていない（塩漬けになっている）案件」を検知し、ChatworkやSlackへ自動でリマインド通知を飛ばす機能の統合。
